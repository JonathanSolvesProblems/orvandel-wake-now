Wake Now: app map

A snapshot of how one click on Orvandel's title screen becomes a guest standing in Lanternfield. Reference route; it reflects the code at the commit named at the bottom and can drift.

What it is

Orvandel is a browser MMORPG: a Three.js client (client/), shared game data (shared/), and the same world simulation run by a Node server (server/) for development and a Cloudflare Worker with Durable Objects and D1 (worker/) live. Wake Now adds one door: a guest is a normal account with a guest mark and a password nobody is told, so every existing system works unchanged. Keep this hero gives the account a name and password and clears the mark.

One action, end to end

Reference route (three stops)

1The button

client/src/screens/login.ts, search data-wake-go. The Wake now block has its own 16+ box; the button stays disabled until it is ticked, and ticking it starts fetching the game code early (onWakeIntent). The click calls api.guest(true) from client/src/net/api.ts.

2The server makes a guest and a hero

server/auth.ts createGuest() (Node) and worker/auth.ts createGuest() (live, inside the per-address AuthDO, which also holds the 3-an-hour limit). Both take the hero and name rules from shared/guest.ts (GUEST_HERO, guestUsername, guestNameCandidates) and write accounts.guest = 1 (migrations/0019_guest.sql).

3Straight into the world

client/src/main.ts, search onWake, then enterWorld(c, waking): the veil reads WAKING_LINE and the select screen is skipped. In the world, client/src/guest-ribbon.ts shows Keep this hero, which posts to /api/account/keep (keepGuest() in both auth files).

To change this, start here

  • Which hero a guest gets: GUEST_HERO and guestBlueprint in shared/guest.ts.
  • How long an unkept guest lasts, and the hourly limit: GUEST_STALE_MS and GUEST_PER_HOUR in shared/guest.ts.
  • What guests cannot do: guestRefusal in shared/guest.ts, called by the REST routes and in server/world/world.ts.
  • The cleanup: sweepGuests in server/auth.ts (Node, hourly in the minute timer) and worker/index.ts (the scheduled() cron, 17 * * * * in wrangler.toml).
  • The tests that hold all of this: tests/verify-guest.ts, plus the Wake now section of tests/cf-local.ts for the Worker.

A practice to reuse

Map once, then build from the map. Before any code, one read-only pass mapped the exact entry points (about 137k tokens). The spec's File Structure section and each checklist slice's Build: and Verify (mechanical): lines carried those paths and symbols, so the build agent started from named functions instead of exploring a 110,000-line codebase. All three slices, across the database, both servers, the client and the tests, took about 451k tokens of build work, one commit each, with a stated check that had to pass before the next slice.

How to apply it on another large project
  • Spend one cheap read-only pass listing entry points, with paths and symbol names, and write them into the plan.
  • Give every step a mechanical check the agent runs itself, so failures surface in the slice that caused them.
  • Keep both halves of a mirrored system (here Node and the Worker) in the same slice, with a parity test, so they never drift.

Run it again

Live: play.jonathansolvesproblems.com. Locally: npm install, then DB_FILE=tmp/dev.db npx tsx server/index.ts and npx vite --config client/vite.config.ts --port 5200, open http://localhost:5200, tick the box and press Wake now. Tests: npx tsx tests/verify-guest.ts.
